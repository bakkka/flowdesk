# Кейс: Flowdesk — подписочный Telegram-бот с админ-панелью

## Контекст

Условный заказчик — эксперт/школа, которая продаёт доступ к материалам через Telegram.
До внедрения: оплата в личных сообщениях, доступ выдаётся вручную по скриншотам, рассылки —
копипастом по списку, статистики нет.

**Боли:** до 4 часов рутины в неделю, потерянные оплаты, нет понимания, какие тарифы и сегменты
работают.

## Задача

Собрать продукт, который закрывает полный цикл:

1. онбординг и выбор языка;
2. продажа подписки внутри бота;
3. выдача контента по уровню тарифа;
4. рассылки по сегментам;
5. прозрачная аналитика для владельца.

## Решение

**Бот** берёт на себя общение и продажу:

- `/start` → выбор RU/EN → меню;
- тарифы с ценами в рублях и Telegram Stars;
- оплата: демо-провайдер + реальные Stars (invoice + `successful_payment`);
- материалы открываются по рангу тарифа, закрытые показывают апселл;
- профиль со статусом подписки и количеством платежей;
- уведомление владельцу о каждом платеже.

**Админка** закрывает операционку:

- дашборд: MRR, активные подписки, конверсия, новые пользователи, выручка и рост по дням;
- пользователи: поиск, фильтры, пагинация, карточка с историей платежей и событий,
  смена тарифа, блокировка;
- тарифы: CRUD, цены, состав, порядок, видимость, счётчики подписчиков;
- рассылки: сегменты, двуязычный текст, черновик/отправка, доставка и open rate;
- контент: материалы с доступом по тарифу, публикация;
- настройки: статус бота, chat id, URL, пересборка демо-данных.

## Архитектура

```
Telegram ──► grammY bot ──┐
                          ├──► Prisma ──► SQLite (dev) / Postgres (prod)
Next.js admin (RSC) ──────┘
   └─ Server Actions ──► Prisma
   └─ cookie locale ──► RU/EN
```

- **Один источник правды** — схема Prisma, общая для бота и панели.
- **Мутации только через Server Actions** — нет отдельного REST-слоя, нет дублирования типов.
- **Сессии** — HMAC-SHA256 подпись в httpOnly cookie, пароли — scrypt.
- **Демо-данные** — детерминированный PRNG: одинаковый набор при каждом `db:seed`.

## Ключевые решения

| Решение | Почему |
| --- | --- |
| Server Actions вместо REST | меньше кода и рассинхрона на проекте такого размера |
| Prisma + SQLite локально | запуск без Docker, переезд на Postgres одной строкой |
| Мок-оплата за адаптером | реальный эквайринг подключается без изменения сценариев бота |
| Собственные SVG-графики | ноль зависимостей, контроль веса и внешнего вида |
| Cookie-locale через route handler | работает без JS, без лишней ревалидации RSC |
| Детерминированный seed | воспроизводимые скриншоты и предсказуемое демо |

## Результат (демо-стенд)

- 1 240 пользователей, 856 платежей, 4 200 событий;
- MRR ≈ 410–425 тыс. ₽ по демо-данным;
- конверсия в платных ≈ 23%;
- 0 ручных выдач доступа;
- рассылка запускается за пару минут вместо часа.

> Числа синтетические и служат для демонстрации интерфейса и логики.

## Сроки

- каркас + схема + seed: 1 день;
- бот: 1 день;
- админка (6 разделов, двуязычность): 2–3 дня;
- полировка, тексты, скриншоты: 1 день.

Итого ≈ 5–6 рабочих дней для одного разработчика.

## Как рассказывать на созвоне (30 секунд)

> «Это бот с подпиской и админкой. Бот продаёт тариф, открывает материалы по уровню доступа и
> собирает базу. Панель показывает деньги и конверсию, позволяет менять тарифы, писать рассылки
> по сегментам и управлять контентом. Всё двуязычное, вход защищён, данные — Prisma. Демо
> открывается по кнопке, можно потыкать прямо при вас.»
